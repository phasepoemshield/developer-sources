# Структура репозитория

Актуально на 24 августа 2026 года.

## Общая модель

`developer-sources` — архив независимых проектов, а не один монорепозиторий со 
сквозной сборкой. Верхний уровень намеренно оставлен плоским: существующие пути
используются в заметках, отчётах и инструментах восстановления. Массовое
переименование каталогов без отдельной миграции может сломать эти ссылки.

```text
developer-sources/
├── README.md
├── docs/
│   └── REPOSITORY_STRUCTURE.md
├── Nightix-1_21_11-master/
├── Polairis-1.21.11-main/
├── Pouche/
├── Pulse/
├── PulseVisuals-1.21.11-sources/
├── Rain/
├── RainVisuals-1.21.11-sources/
├── Releon/
├── Research/
├── Rockstar/
├── Skycore/
├── Wild/
├── Wonderful/
├── Zenith by @wealtiteam & @soezproject/
└── destra-backup/
```

## Связь с Flux Visuals

Последний аудит подтвердил, что главный проект и архив полностью разделены:

| Контур | Канонический checkout | GitHub-репозиторий | Роль |
|---|---|---|---|
| Flux Visuals | `/Users/timur/Developer/FluxVisuals-dev` | `phasepoemshield/FluxVisuals-dev` | Главный продукт, Minecraft 1.21.8 |
| Developer Sources | `/Users/timur/Developer/developer-sources` | `phasepoemshield/developer-sources` | Приватный исследовательский архив версий 1.16.5–1.21.11 |

Между контурами нет:

- общего Git-корня или общей истории коммитов;
- Git submodule/`.gitmodules`;
- символических ссылок между рабочими деревьями;
- Gradle-зависимости или общего root build;
- автоматического копирования, commit или push.

Следствия этой границы:

- изменение или push `developer-sources` не меняет Flux Visuals;
- ни один каталог из таблицы ниже не является модулем главного проекта;
- наличие более новой версии Minecraft в архиве не обновляет целевую версию
  Flux Visuals;
- отчёты и README архива описывают конкретный восстановленный снимок, а не
  текущее состояние продукта;
- при конфликте сведений приоритет имеют текущий checkout Flux Visuals, его
  `AGENTS.md`, `README.md`, `docs/PROJECT_STATE.md` и фактическая сборка.

### Протокол переноса в главный проект

1. Найти в архиве конкретного владельца нужного поведения, ресурса или
   алгоритма.
2. Перенести только необходимую часть и адаптировать её под текущие API,
   профили, lifecycle и render-контракты Flux Visuals.
3. Не переносить runtime-кэши, чужие конфиги, встроенные credentials и
   восстановленные рекламные/network endpoints.
4. Коммитить результат только в `FluxVisuals-dev`; архив и главный проект имеют
   независимые ветки и историю.
5. Отдельно фиксировать уровень доказательств: static check, build, startup,
   runtime, visual acceptance и persistence не заменяют друг друга.

Прямое совпадение кода с донором не считается целью. Источник может объяснить
поведение, но итоговая реализация должна оставаться нативной для Flux Visuals и
не нарушать работающие механики главного проекта.

## Типовая структура восстановленного проекта

Не все каталоги содержат каждый из перечисленных разделов, но значения имён
одинаковы во всём архиве:

| Путь | Что хранится |
|---|---|
| `src/main/java` | Основной редактируемый Java source set |
| `src/main/kotlin` | Основной Kotlin source set, если он восстановлен |
| `src/main/resources` | Fabric metadata, mixins, assets и runtime-ресурсы |
| `src/recovered-java` | Альтернативный Java-дамп декомпилятора; может не компилироваться |
| `src/recovered-kotlin` | Читаемый Kotlin-oriented дамп; может содержать synthetic-конструкции |
| `reference/` | Оригинальные и remapped артефакты, используемые как доказательная база |
| `reports/` | Покрытие, карты имён, результаты статических и runtime-проверок |
| `tools/` | Воспроизводимые скрипты remap, rename, patch и анализа bytecode |
| `libs/` | Локальные зависимости или runtime-артефакты, необходимые конкретному проекту |
| `gradle/wrapper/` | Закреплённая версия Gradle wrapper |

## Правила порядка

### Что хранить в Git

- исходники, ресурсы, Gradle-конфигурацию и wrapper;
- локальные библиотеки, если без них нельзя воспроизвести сборку;
- оригинальные/remapped артефакты в `reference/`, когда они являются частью
  процесса восстановления;
- отчёты, карты имён и инструменты, объясняющие происхождение исходников.

### Что не хранить в Git

- `build/`, `.gradle/`, `out/`, `.cache/`, `tools_out/`;
- `run/`, `saves/`, `screenshots/`, `crash-reports/` и логи;
- `.idea/`, `.vscode/`, `.DS_Store` и временные файлы;
- `.env` и локальные credential-файлы.

Корневой `.gitignore` покрывает эти категории для всех вложенных проектов.
Локальные `.gitignore` допустимы только для специфичных артефактов конкретного
проекта.

## Безопасность и публикация

Восстановленные исходники могут содержать встроенные токены, HMAC-ключи,
webhook-адреса или приватные endpoints из исходного JAR. Поэтому:

1. репозиторий должен оставаться приватным, пока секреты не инвентаризированы;
2. перед каждым изменением видимости нужен повторный secret scan;
3. реальные значения нельзя копировать в документацию, issues или сообщения
   коммитов;
4. удаление значения из текущего файла не очищает историю Git — для уже
   опубликованного секрета нужны ротация и отдельная очистка истории.

## Добавление нового проекта

1. Создайте один верхнеуровневый каталог с однозначным именем и версией.
2. Добавьте локальный `README` с происхождением, версией Minecraft и уровнем
   проверки: static, build, startup, runtime и visual acceptance.
3. Не переносите build/runtime-кэши.
4. Добавьте строку в индекс проектов выше.
5. До коммита проверьте размер файлов и наличие секретов.
